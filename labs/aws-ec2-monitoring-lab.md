# AWS Hands-On Lab: Monitor an EC2 Instance

**Platform:** AWS Skill Builder (Vocareum)
**Date completed:** November 7, 2026
**Duration:** ~60 minutes
**Region:** US West (Oregon) — us-west-2

## Overview

This lab builds a basic monitoring and alerting pipeline for an EC2 instance. It simulates what happens when a malicious actor (or runaway process/malware) spikes CPU utilization on a server, and verifies that the monitoring stack actually catches it and notifies a human.

**Scenario:** An EC2 instance named `Stress Test` has its CPU driven to 100% with a stress-testing command. A CloudWatch alarm watching `CPUUtilization` should trip, and an SNS email notification should land in the inbox.

## Objectives

- Create an Amazon SNS notification
- Configure a CloudWatch alarm
- Stress test an EC2 instance
- Confirm that an Amazon SNS email was sent
- Create a CloudWatch dashboard

## Architecture

```
EC2 (Stress Test instance)
     │  CPUUtilization metric (1-min period, Average)
     ▼
CloudWatch Alarm  ──(threshold: > 60%)──▶  SNS Topic "MyCwAlarm"
     │                                            │
     ▼                                            ▼
CloudWatch Dashboard                      Email Subscription
(LabEC2Dashboard)                         (confirmed via email link)
```

## Task 1: Configure Amazon SNS

1. Opened Amazon SNS in the console and created a **Standard** topic named `MyCwAlarm`.
2. Created a subscription on that topic:
   - Protocol: **Email**
   - Endpoint: account email address
3. AWS sent a subscription confirmation email ("AWS Notification - Subscription Confirmation"). Opened the email and clicked **Confirm subscription**.
4. Verified in the console that the subscription status changed from `Pending confirmation` to **Confirmed**.

**Result:** The topic can now deliver alerts to the subscribed email address.

## Task 2: Create a CloudWatch Alarm

1. In CloudWatch → Metrics → All metrics → **EC2 → Per-Instance Metrics**, located the `CPUUtilization` metric for the `Stress Test` instance and confirmed the baseline graph (~0%, idle).
2. Created a new alarm on that same metric:
   - **Statistic:** Average
   - **Period:** 1 minute
   - **Threshold type:** Static
   - **Condition:** `CPUUtilization` **Greater than** `60`
   - **Notification:** On **In alarm**, notify the existing SNS topic `MyCwAlarm`
   - **Alarm name:** `LabCPUUtilizationAlarm`
   - **Description:** CloudWatch alarm for Stress Test EC2 instance CPUUtilization
3. Created the alarm — initial state: `Insufficient data` (no datapoints yet).

**Result:** `LabCPUUtilizationAlarm` is armed and will fire to the `MyCwAlarm` SNS topic the moment average CPU exceeds 60% for one 1-minute datapoint.

## Task 3: Stress Test the EC2 Instance

1. Opened a terminal session on the `Stress Test` instance via **AWS Systems Manager → Session Manager** (using the `EC2InstanceURL` from the lab's connection details).
2. Ran:
   ```bash
   sudo stress --cpu 10 -v --timeout 400s
   ```
   This forked 10 CPU-hogging worker processes for 400 seconds, driving utilization toward 100%.
3. Watched the CloudWatch alarm page and refreshed periodically.
4. After a few minutes, `LabCPUUtilizationAlarm` transitioned from `OK` to **`In alarm`**, with the condition showing `CPUUtilization > 60 for 1 datapoints within 1 minute`.
5. Checked the subscribed email inbox and confirmed receipt of:
   > **Subject:** ALARM: "LabCPUUtilizationAlarm" in US West (Oregon)
   > Threshold Crossed: 1 out of the last 1 datapoints [...] was greater than the threshold (60.0).

**Result:** End-to-end alerting confirmed — CPU spike → alarm state change → SNS email delivered.

## Task 4: Create a CloudWatch Dashboard

1. Created a new custom dashboard named `LabEC2Dashboard`.
2. Added a **Line** widget using the `CPUUtilization` metric (EC2 → Per-Instance Metrics) for the `Stress Test` instance.
3. Saved the dashboard.

**Result:** A reusable dashboard (`LabEC2Dashboard`) now gives a one-click view of CPU utilization for the `Stress Test` instance, showing the spike generated by the stress test.

## Key Takeaways

- **CloudWatch alarms are metric-driven, not log-driven** — they watch a statistic (here, Average CPUUtilization) over a defined period and transition state only once the condition holds for the configured number of datapoints.
- **SNS subscriptions must be confirmed** before they'll deliver anything — an unconfirmed email subscription silently does nothing.
- **`stress` is a convenient, repeatable way to simulate load/attack conditions** for testing monitoring and alerting pipelines without needing an actual incident.
- **Dashboards are for humans, alarms are for automation** — the dashboard doesn't trigger anything by itself; it's a visualization layer on top of the same metrics the alarm watches.
- This pattern (metric → alarm → SNS → email) is the minimal viable building block for most AWS operational alerting, and extends naturally to Lambda, Auto Scaling, or incident-management integrations as the "action" instead of (or in addition to) email.
